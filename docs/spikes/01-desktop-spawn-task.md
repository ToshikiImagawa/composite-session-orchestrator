# Spike 01: Claude Desktop の spawn_task

PRD 6 章の未検証事項を確認する。結果によって FR_009, FR_010, FR_016, FR_032, FR_036, IR_002 の
Desktop 環境での扱いが変わる。

## 手順（ダミーリポジトリで実施）

1. 親セッションで spawn_task を呼び、子に「指定パス以外にファイルを書け」と指示する
2. hooks で deny されるかを確認する
3. 親から子へのメッセージ送信と停止を試す
4. 子の完了後に結果を取得し、セッション ID を確認する
5. 最後に親セッションを閉じ、子の挙動を確認する

### 手動確認で分かった、設計への注意

- **子を閉じる・削除すると、子の中身が読めなくなる**（B2・B5）。子を閉じると子のトランスクリプトは残らず、削除すると `get_session`・`list_events` も not found になる。子の結果を残せるのは、daemon の記録（受信箱・イベントログ・`report.done` の本文）だけ。
- **ワークツリーは、子を閉じても削除しても残り、次の子が再利用することがある**（B3・B5）。ワークツリーの有無を子の生死の目印にできず、回収を Desktop の削除に任せられない。
- **メッセージで子の作業を途中で割り込めない**（B4）。処理中の子は、ターンが終わってから読む。止めた子からは `PostToolUse`・`Stop` がフックに出ない。
- **アプリの再起動のあとは、子が新しいプロセスになる**（B6）。アプリが自動で送る再開のメッセージは、フックでは人間の入力と区別できない。シェルの変数に入れたトークンは失われる見込み。
- **子は届いた指示を断ることがある**（B6。FR_009）。届いたことの確認とは別に、受け入れられたことの確認が要る。

### メッセージ配信の制約（項目 2）

- 公式文書は 2 つの経路を述べており、どちらが Desktop の親子に当たるかは未確認。
  - Desktop の「Work across sessions」: 受信側が作業中なら、メッセージは保留され、現在の作業が終わってから読まれる [1]。
  - cross-session-messaging（`SendMessage`）: 受信側は、アクティブなターン中のツール呼び出しの合間にメッセージを読む。実行中のツールは中断されない [2]。
  - 保留の長さは経路で違う（作業の完了まで／ツール呼び出しの合間）。追加指示の即時性は保証できない。
- 受信側が `crossSessionInbound` を `refuse` にしていると、メッセージは破棄される [1][2]。
- `crossSessionInbound` が未設定のときは、送信側と受信側の権限モードの組み合わせで配信・保留が決まる [2]。受信側が権限プロンプトを出す側なら配信される。送信側が「権限を迂回する側」を名乗ったときだけ保留される。受信側が迂回する側なら、迂回を名乗らない送信側のメッセージは保留される。
- Desktop と VS Code のセッションは承認ダイアログを出せず、保留されたメッセージは `dialogExpiry`（既定 5 分）を過ぎると破棄される [2]。
- 送信側が Auto、受信側が Bypass の組み合わせでは、メッセージが保留・破棄され得る（公式文書からの推論。組み合わせの正確な分類は手動確認が要る）。この場合 FR_009 の「追加指示が届く」前提が崩れる。

## 手動確認の手順（Desktop で人間が実施）

### 準備と記録

- ダミーリポジトリ（git 管理）を用意する。
- 次の 3 つを用意する。
  - Desktop の `claude_desktop_config.json` に登録した stdio MCP サーバー（Issue [4] で欠けると報告された種類）
  - プロジェクトの `.mcp.json` のサーバー
  - claude.ai のコネクタ（任意）
- plugin に PreToolUse フックを入れ、Write を deny し、各呼び出しを `~/spike01-hook.log` に 1 行ずつ追記させる。書式は `<ISO 時刻> <hook_event_name> <session_id> <tool_name> <decision>`（フックの入力 JSON から取る）。
- 記録欄: Desktop のバージョン、Claude Code のバージョン、OS、権限モード（親・子）。

### 手順と判定基準

1. **項目 4**: 親に「spawn_task で、`/tmp/x` にファイルを書く子を作って」と頼む。チップを「ワークツリーで開始」と「ローカルで開始」の両方で起動する。子が最初の人間のメッセージを受け取る前に、子に `ToolSearch` で deferred tools を調べさせ、(a) 上の 3 種類の MCP ツールが見えるか、(b) `~/spike01-hook.log` に行が出るか、(c) 書き込みが deny されるかを見る。その後に子へメッセージを送り、見え方が変わるかも記録する。
   - 可: (a) が 3 種類とも見え、(b)(c) が成立する。
   - 条件付き: 最初のメッセージ後にだけ成立する（#67432 と同じ挙動）。
   - 不可: メッセージ後も成立しない。
   - 追加で見る点: spawn_task の `prompt` が「人間のメッセージ」として扱われるか。扱われないなら、最初のメッセージ前は MCP が無く、FR_032 の紐付けが実行できない可能性がある。
2. **項目 1・2**: 親に「他のセッションを一覧して」「その子にメッセージを送って」「その子を止めて」と頼む。子が処理中のときと、アイドルのときの両方で行う。
   - 使えた操作名とエラー文を記録する。
   - 「停止」は、使えた／使えなかった／保留された、のいずれかで判定する。
   - メッセージは、子がツール呼び出しの合間に読んだ／現在の作業の後に読んだ／届かなかった（破棄）、のいずれかで判定する。
   - 親と子の権限モードの組み合わせ（Manual／Auto／Bypass）を変えて繰り返し、5 分以上放置したときの破棄も確認する。
   - Desktop の Work across sessions が見えるのは、Code タブの local・SSH・WSL セッションだけ。CLI、VS Code、クラウドのセッションは対象外なので、親子とも Desktop の Code タブで起動する。
   - 記録欄に「どの配信経路だったか（Desktop 内蔵 / SendMessage）」の行を設け、メッセージごとに書く。
3. **項目 3**: 子を完了させ、親に「子の結果を読んで」と頼む。取れた内容（最終メッセージ、差分、コミット）を記録する。あわせて親に「子が止まったら教えて」と頼み、`notify_when_idle` の通知が届くかを確認する。
   - 可: 完了と結果の両方を、親が人間の操作なしで取得できる。
   - 条件付き: 結果は読めるが、完了の通知は来ない（読みに行く必要がある）。
4. **項目 5**: spawn_task に別ディレクトリの `cwd` を渡して起動する。子の `pwd` と `git worktree list` を見る。
   - 可: `git worktree list` に新規ワークツリーが出て、子の `pwd` がその中にある。
   - 条件付き: `cwd` は効くが、ワークツリーにならず主チェックアウトで始まる。
5. **項目 6**: 一覧・読み取りの結果と画面に session ID が出るかを見る。
   - 可: 出た値が、`~/.claude/projects` 配下のトランスクリプトのファイル名と一致する。
   - 不可: 値が出ない、または一致しない。
6. **項目 7**: 子に「`sleep 600` を実行し、終了時刻を `/tmp/spike01-end` に書け」と頼み、実行中に親を閉じる（macOS は Cmd+W、Windows は Ctrl+W、またはサイドバーのアーカイブ）。子のプロセスは `pgrep -f` で探さず、子のシェルが記録した PID と、その親子関係（`ps -o pid,ppid,etime`）で追う（`pgrep -f` は自分自身も数える。Spike 02 と同じ注意）。`sleep 600` は、閉じてから `ps` で確認するのに十分な長さ。アプリを再起動した後も確認する。
   - 可（子が存続）: 子が最後まで走り、`/tmp/spike01-end` が書かれる。
   - 不可（子が停止）: プロセスが消え、ファイルが書かれない。
   - ワークツリーの有無も記録する。
