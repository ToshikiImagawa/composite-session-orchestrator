# Spike 01: Claude Desktop の spawn_task

PRD 6 章の未検証事項を確認する。結果によって FR_009, FR_010, FR_016, FR_032, FR_036, IR_002 の
Desktop 環境での扱いが変わる。

## 手順（ダミーリポジトリで実施）

1. 親セッションで spawn_task を呼び、子に「指定パス以外にファイルを書け」と指示する
2. hooks で deny されるかを確認する
3. 親から子へのメッセージ送信と停止を試す
4. 子の完了後に結果を取得し、セッション ID を確認する
5. 最後に親セッションを閉じ、子の挙動を確認する

## 確認項目と結果

## 手動確認の手順（Desktop で人間が実施。ダミーリポジトリ、フック付き）

準備: ダミーリポジトリに `.mcp.json`（任意の stdio MCP サーバー）と、PreToolUse で Write を deny し全フック呼び出しをログに残す hook を入れた plugin を用意する。

1. **項目 4**: 親で「spawn_task で、`/tmp/x` にファイルを書く子を作って」と頼み、チップを「ワークツリーで開始」「ローカルで開始」の両方で起動する。子が最初のメッセージを送る前に、(a) MCP ツールの一覧、(b) フックのログ、(c) 書き込みが deny されるか、を見る。deny されれば可、フックが走らず MCP が無ければ不可。最初のメッセージ後に変わるかも記録する。
2. **項目 1・2**: 親に「他のセッションを一覧して」「その子にメッセージを送って」「その子を止めて」と頼む。使えた操作名とエラーを記録する。子が実行中の最中に送り、保留されるか割り込めるかを見る。
3. **項目 3**: 子を完了させ、親に「子の結果を読んで」と頼む。取れる内容（最終メッセージ、差分、コミット）を記録する。
4. **項目 5**: spawn_task に別ディレクトリの `cwd` を渡し、子の `pwd` と `git worktree list` を確認する。
5. **項目 6**: 一覧/読み取りの結果と UI に session ID が出るか。出る場合、`~/.claude/projects` 配下のトランスクリプト名と一致するかも確認する。
6. **項目 7**: 子が長い処理（`sleep 300` を含む）を実行中に、親を Cmd+W で閉じる／アーカイブする。子の画面、プロセス（`ps`）、ワークツリーの有無を確認し、アプリ再起動後も記録する。

## 結論

公開情報だけでは確定しない。以下は現時点の評価で、項目 4・6・7 の手動確認後に確定する。

- **FR_036**（操作代行）: 親から子へのメッセージ送信とアーカイブは Desktop の機能として存在するが、停止の専用操作は確認できない。停止が必要な場面は、受信箱経由で親（または人間）に代行させる前提が妥当。現行の設計方針を維持できる。
- **FR_009**（追加指示）: 可能。ただし受信側が処理中なら現在のターン終了後まで保留される。追加指示の即時性は保証できない。
- **FR_010**（停止）: 即時停止は期待できない。停止が必要なら FR_036 の代行か、FR_014 による範囲外の拒否で安全を確保する。
- **FR_016**（脱線の切り出し）: spawn_task による子の生成は可能で、`cwd` も渡せる。ワークツリー作成は人間のチップ操作に依存し、自動化できない。
- **FR_032**（Desktop の子の生成と紐付け）: 生成の戻り値は `task_id` のみで session ID がなく、紐付けは別の手段（子からの自己報告や名前）が必要になる。項目 6 の手動確認が要る。
- **IR_002**（フックによる記録と拒否）: 最大のリスク。ワークツリーのセッションは設定とフックを主チェックアウトから読むため継承される見込みはあるが、spawn_task の子で MCP が初期段階で欠ける不具合が報告されており、フックの継承は未検証。項目 4 が否なら、Desktop の子には範囲拒否を保証できないため、代替（子の最初のメッセージ送信後に有効化を確認する、起動直後は作業させない）が必要になる。
- **NFR_002**（再起動後の復元）: 親を閉じたときの子の挙動は不明。項目 7 の結果次第で、状態の復元を子の存続に依存させられるかが決まる。
