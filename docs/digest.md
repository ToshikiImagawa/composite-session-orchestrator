# 中間統合ノードの配下の要約（`digest`。T24・FR_013）

受信箱は、呼び出し元の部分木の項目を、平らに返す（`visibleState`）。深い木では、根の受信箱に、葉の項目が大量に並ぶ。
**中間統合ノード（根でない統合ノード）ごとに、配下の状況を 1 件の要約（`digest`）に畳み**、優先度をつけて、上位の受信箱へ送る。
この文書は、core の部分（PR1。型・fold の規則・純粋関数）。発行する仕組み（周期・冪等・解決）は、daemon の PR2。

## 要約の項目

- 受信箱の項目の種類 `digest`（`InboxKind`）。`inbox.added` の `kind: "digest"`。
- **`nodeId` は、中間統合ノード自身**（上位から見たときに、どのノードの要約か分かる）。fold は、根・実装などのノードを `invalidDigestOwner` で拒否する。
- **`priority`**（`inbox.added` の任意の項目。**`digest` だけが持ち、必ず持つ**。`PRIORITIES` のどれか）。そのほかの種類が持つと `invalidPayload`。
  優先度は、種類で決まる既存の規則（`INBOX_KIND_PRIORITY`）の代わりに、項目の `priority` で決まる（`priorityOf`）。整列（`sortInbox`・FR_012）は、`priorityOf` を使う。
- `ref` は持てない（記録を指さない）。**`summary` は必ず持つ**（持たない `digest` は `invalidPayload`）。`INBOX_SUMMARY_MAX`（200）文字以下。
- **前提: `digest` の項目を作るのは、daemon の発行器だけ**で、`summary` は `digestOf(...).summary` の値をそのまま書く。fold は、`summary` が `digestOf` の結果かは検査しない
  （許可文字による検査はしない）。発行器の試験が、`summary === digestOf(...).summary` を毎回突き合わせる（T24-d の完了条件）。人間・子・統合ノードが、`digest` を書く窓口の操作はない。
- 保存データの版 `STATE_VERSION` は 10（受信箱の項目に `priority` を追加）。mcp の受信箱の応答は、`priority` が `digest` だけにあり、`PRIORITIES` のどれかであることを検査する（不正な項目は除外）。

## 中身（`digestOf(state, nodeId, nowMs)`）

純粋関数。要約を出す対象（`digestTargets`）は、**根でない統合ノードで、動作中か待機中のもの**。完了・停止したノードには出さない。

- 配下（自分を含まない）のノードの数と、状態別の件数。
- 配下（**自分を含む**。持ち主が `archived` のものは除く）の、未解決の項目の、グループ別の件数（要判断・範囲違反・失敗・完了・進捗・情報）。未回答の判断要求・未判定の拡張要求の数。
- 最優先の項目の ID（`LIMITS.digestTopItems` = 3 件。優先度・時刻・ID の順）。最も古い「要判断」の経過分。
- **優先度 = 配下の未解決の項目の最高の優先度**（要判断 > 失敗 > 完了 > 進捗 > 情報）。**未解決の項目がなければ、要約はない**（`undefined`）。
- 数える項目は、要約以外（要約は、ほかの要約を数えない。再帰しない）。別の部分木の項目は数えない。
- `fingerprint`: 時間に依存しない事実（件数・状態・最優先の項目）の指紋。同じなら、要約を出し直さない（経過分は含めない）。

## 信頼できない文字列を、上へ流さない

要約には、**子が影響できる自由な文字列を、一切含めない**。含めるのは、件数・状態名・識別子（ノード ID・受信箱の項目の ID。どちらも `isId` を通ったもの）・経過分だけ
（パス・ブランチ名・報告の本文・判断の質問・項目の `summary` は、含めない）。文面は、`digestOf` が組み立てる（決定的。同じ状態なら同じ文面）。長いときは、最優先の項目の ID を減らして収める。
エージェントが書く要約は、作らない。

## 発行（daemon の発行器。T24-d）

`packages/daemon/src/digest-issuer.ts`（`createDigestIssuer`）。**既定で有効**（既存の受信箱の項目に、追加で 1 件出すだけで、隠さない）。設定 `digest` で調整・無効化できる。

```json
{ "digest": { "enabled": true, "intervalSec": 30, "minIntervalSec": 60, "maxPerRun": 20 } }
```

| 項目 | 意味 | 既定 |
| --- | --- | --- |
| `enabled` | `false` で、要約を出さない | `true` |
| `intervalSec` | 周期（5〜3600 秒）。最初の実行は、起動から 1 周期後 | 30 |
| `minIntervalSec` | 中間統合ノードごとの、要約の最短の間隔（10〜3600 秒。単調時計で測る） | 60 |
| `maxPerRun` | 1 周期に出す要約の数の上限（1〜100）。超えた分は、次の周期に出す | 20 |

- **契機**: 周期ごとに、ログが前回の確認から進んでいたら（または、間隔のために見送った要約があれば）、対象（`digestTargets`）を調べる。進んでいなければ、何もしない。
- **出し直さない**: 前回の要約と事実（`fingerprint`）が同じなら、出さない。項目の ID は、`(ノード, 指紋, そのノードの要約の通し番号)` から決まる（再実行・再起動でも、重複しない）。
  要求 ID は、本文（要約の文面）も含めて決める（**同じ要求 ID が、違う本文で再送されない**。時刻が進んで文面の経過分が変わると、要求 ID も変わる）。
- **事実が変わっても、出し直すのは、次のいずれかのときだけ**（記録の増え方を抑える）: ①**優先度が変わった**とき、②**要判断の件数が変わった**とき、③**前回から 10 分以上たった**とき（壁時計）。
  最優先の項目の ID や、状態別の件数が変わっただけでは、10 分たつまで出し直さない（ログが進まなくても、次の周期に調べ直す）。ノードごとの最短の間隔 `minIntervalSec` も、守る。
- **未解決の要約は、ノードごとに常に 1 件**: 新しい要約を出せたら、前の要約を system が解決済みにする。**追記と解決は、分けて扱う**:
  最新の未解決の要約が、今の事実のものなら、追記はせず、それ以外の未解決の要約だけを解決する。**解決に失敗したら、「再試行が必要」の印を立て、ログが進まなくても、次の周期に再試行する**
  （解決の失敗が続いても、同じ事実の要約が積み上がらない）。
- **解決する**: 配下の未解決の項目がなくなったとき、ノードが完了・停止など（対象でなくなったとき）は、出ている要約を system が解決済みにする。新しい要約は出さない。
- **書くのは `digestOf` の結果だけ**（`summary`・`priority`）。試験が、`summary === digestOf(...).summary` を毎回突き合わせる。子が影響できる文字列は入らない。
- 追記に失敗しても、止まらない（`digest.failed` に記録し、次の周期に再試行する。前の要約は解決しない）。ログが壊れた（fatal）後は動かさない。`stop` は、実行中の 1 回が終わるのを待つ。
- 記録の名前: `digest.issued`・`digest.failed`・`digest.resolveFailed`・`digest.skipped`・`digest.error`。
- **記録の増え方**: 要約は、解決済みになっても、記録（イベントログ）には残る。1 件の要約は、2 つのイベント（`inbox.added`・`inbox.resolved`。合わせて約 0.5 KB）。
  **見積り**: 中間統合ノード 1 つあたり、期間 `T` に増えるイベントは、**最大でも `2 × (C + ⌈T / 10 分⌉)` 個**。`C` は、その期間の、優先度・要判断の件数が変わった回数
  （どちらも、`minIntervalSec` が下限）。例: 変化が少ない（`C` ≒ 0）1 日で、1 ノードあたり最大 288 個（約 70 KB）。木に中間統合ノードが 10 個あれば、最大 700 KB 台。
  事実が変わり続けても、この上限を超えない。要約の項目は、最終削除（木の削除）で、木のほかのノードの行と一緒に消える。
- `stop()` のあとに `start()` し直しても、周期は二重にならない（古い周期は、世代の番号で無効になる）。

### アーカイブ済みの枝の項目（T24-a。決定）

**持ち主のノードが `archived` の、未解決の項目・未回答の判断・未判定の拡張要求は、要約の件数・優先度・最優先の項目に入れない**（3 つに、同じ規則を当てはめる。件数が食い違わない）。
アーカイブは、回収まで済んだ終わりの状態で、残ったものは古い記録だから。ノード数・状態別の件数には、アーカイブ済みのノードも数える。
配下の項目が、アーカイブ済みの枝のものだけになったら、要約はなくなり、出ている要約は、発行器が解決する。
`reclaimable` より前の状態（停止した枝など）のものは、除かない（人間が見る必要がある）。**アーカイブのときに、system が項目を自動で解決する案は、採らない**（記録の意味を変えない）。

## 中間統合ノードを起こす（T24-w。daemon の `wake.ts`）

**既定で無効。有効にすると、配下に新しい項目が届くたびに、動作中の中間統合ノードへ指示を送るので、追加のターンと予算（`maxBudgetUsd`）を使う。**
受信箱を見に行かない中間統合ノードが、配下の `done`・`failure` などに気づかないままになるのを防ぐ。設定 `wake`:

```json
{ "wake": { "enabled": true, "intervalSec": 15, "minIntervalSec": 60, "maxPerRun": 10, "maxPerHour": 120 } }
```

| 項目 | 意味 | 既定 |
| --- | --- | --- |
| `enabled` | `true` で有効（**既定は無効**） | `false` |
| `intervalSec` | 周期（5〜3600 秒） | 15 |
| `minIntervalSec` | ノードごとの、起こす最短の間隔（10〜3600 秒。単調時計） | 60 |
| `maxPerRun` | 1 周期に起こす数の上限（1〜100） | 10 |
| `maxPerHour` | 全ノード合計で、1 時間に起こす数の上限（1〜1000） | 120 |

- **対象**: 根でない統合ノードで、状態が `running`、アダプタが管理しているもの。`waiting`（判断待ち。回答の配送で再開する）・完了・停止・停止の途中・アダプタが管理していないノード（根・daemon の外で動くノード）・判断待ちで止めている子は、起こさない。
- **契機**: 対象の直接の子の、未解決の項目で、種類が `decision`・`violation`・`failure`・`stopIncomplete`・`done`、かつ、前回起こした根拠の `seq` より新しいもの（持ち主が `archived` のものは除く）。
  `progress`・`info`・`answer`・`digest` では起こさない。深い枝の項目は、その枝の統合ノードがまず起き、そこから上へ要約（digest）が上がる。要約の発行（T24-d）には連動させない（要約は、優先度などが変わったときにしか出ず、同じ帯の新しい項目で起こしそびれるため）。
- **指示**: 固定の 1 行（`WAKE_TEXT`。「受信箱に、配下の新しい項目が届いた。inbox_fetch で確かめて、必要な操作をしてください。」）。**子の文字列・ID・件数を一切含めない**。送り方は、判断の回答の配送と同じ（`node.instructed`〔system〕→ `node.send` と同じ配送 → `node.instructionDelivered`）。
- **冪等**: 要求 ID は `wake-<ノード>-<根拠の最大の seq>`（決定的）。同じ要求は、重複して記録も配送もしない。「最後に起こした seq」は**メモリだけ**に持つ（再起動のあとは、未解決の項目から作り直す）。**起動の直後の 1 周期目も、`minIntervalSec` を守る**（再起動の直後に、一斉に起こさない）。
- **配送の失敗**: `wake.failed` に残し、次の周期（間隔を守って）に再試行する。同じノードで 3 回続けて失敗したら、新しい項目が届くまで再試行しない（`wake.gaveUp`）。**受信箱の項目は作らない**（作ると、そのノードの親を起こす連鎖になるため）。
- **記録（ログ）の名前**: `wake.woken`・`wake.failed`・`wake.gaveUp`・`wake.nearLimit`（ノードごとの 1 時間の起こした数が、上限〔`minIntervalSec` で 1 時間に起こせる最大〕の 8 割に近づいた）・`wake.summary`（1 時間ごと。ノードごとの起こした数・失敗・打ち切り。何もなければ出さない）。
- **束ねる（ターンの間に積み上げない）**: 起こす指示を配送したあと、**そのノード自身の操作（そのノードが `actor` のイベント）が 1 つもない間は、新しい項目が届いても、新しく起こさない**。ノードが起きて何かを操作したら、次を起こせる。
  何も操作しないまま起きているノードを、永久に起こさなくならないように、**10 分たてば、操作がなくても、また起こせる**。
- **費用（有効にする前に読む）**: 起こすたびに、そのノードのセッションが 1 ターン動く（トークンと予算を使う）。**上限の見積り**: ノードごとに、1 時間に最大 `⌊3600 / minIntervalSec⌋` 回（既定で 60 回。束ねるので、実際は、ノードが操作した回数以下）。全体では `maxPerHour`（既定 120）回。
  1 時間の追加の費用の目安は「**1 ターンの費用 × 起こした回数**」で、上限は「1 ターンの費用 × `min(maxPerHour, ノード数 × ⌊3600 / minIntervalSec⌋)`」。さらに、**子ごとの `maxBudgetUsd`（既定 5 USD）が、そのノードの合計の上限**になる（超えるとノードは止まる）。
  費用を抑えたいときは、`minIntervalSec` を長く（例 300）・`maxPerHour` を小さくする。
- **記録（ログ）の増え方**: 1 回起こすと、2 つのイベント（`node.instructed`・`node.instructionDelivered`）。1 時間に、全体で最大 `2 × maxPerHour` 個（既定で 240 個）。
- **`wake.nearLimit`・`wake.hourlyLimit`**: ノードごとの 1 時間の回数が、上限の 8 割に近づくと `wake.nearLimit`、全体の `maxPerHour` に達すると `wake.hourlyLimit`（どちらも、時間の窓〔1 時間〕ごとに 1 回だけ）。
- **注意（再起動の直後）**: 「最後に起こした seq」と束ねるの状態は、メモリだけに持つ。**再起動の直後に、すでに起こした項目のために、1 度余計に起こす場合がある**（配送済みの同じ要求〔`wake-<ノード>-<seq>`〕は、重複して送らない。再起動で子のセッションは失われるので、実際に起こせるのは、起動し直した後のノードだけ）。
