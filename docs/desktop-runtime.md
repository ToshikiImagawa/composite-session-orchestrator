# Desktop のランタイムアダプタ（T20）

Desktop の子は、統合セッションが Desktop のタスク生成機能で起動する。daemon は子を直接操作できないので、
`DesktopRuntimeAdapter`（`packages/daemon/src/sdk/desktop-adapter.ts`）は、次のように振る舞う。

## 能力表（実機確認の前の控えめな値。B の結果の反映は未実施。T20 で見直す）

| 項目 | 値 | 意味 |
|:--|:--|:--|
| `send` | `unsupported` | daemon から直接指示を届けない。`node.send`・判断の回答の配送・起こす（wake）・差し戻しは、記録する前に失敗する（または届けない） |
| `stopGraceful`・`stopImmediate` | `false` | 直接は止めない |
| `stopDelegated` | `true` | 停止は、受信箱を通じて親に代行を依頼する（停止未完了として記録し、受信箱の `stopIncomplete` の項目に依頼の文面を出す） |
| `hooks` | `unverified` | Desktop の子にフックが効くかは未確認（Spike 01 の項目 4） |
| `sessionId` | `false` | タスク生成の戻り値に、子のセッション識別子がない |

値は `DESKTOP_CAPABILITIES` の 1 か所にある。Spike 01 の項目 1〜7 の確認が済んだら、値を差し替えるだけでよい。

## フックのゲート

フックが確認済み（`hooks: "ok"`）でない間は、アダプタは子の起動（`start`）を拒否する。拒否の文面には、`hooks` の値（未確認・未対応）を出す。
既定は有効で、設定ファイルの `desktopRequireVerifiedHooks: false` でのみ外せる（API では変えられない）。外したときは、起動のたびに警告を記録する。

**ゲートは、子を daemon の管理下に入れないことで効く。daemon を経ない起動（統合セッションが、daemon を通さずに Desktop のタスク生成機能を直接呼ぶ）は、止められない。**
ゲートが守るのは、daemon が管理する子に、作業範囲外の拒否（FR_014）なしで作業を許すことがない、という点だけである。

## 停止の代行依頼の文面

手順を先に、対象のノードの ID を後ろに置く。受信箱の要約の上限（200 文字）で切られても、手順は残る。ID が最長（128 文字）でも、手順と ID の両方が収まる。

## 停止の宣言（`node.confirmStopped`）

親が代行依頼に従って Desktop でタスクを止めた（またはアーカイブした）ら、人間か、そのノードの祖先の統合ノードが `node.confirmStopped`
（`{ nodeId, note? }`）で宣言する。1 トランザクションで、次を記録する。

1. `node.stopDeclared`（宣言した者は封筒の `actor`、根拠は `note`）。状態の `stopDeclarations` に残る。
2. `confirmStopped`（`stopIncomplete` → `stopped`）。
3. そのノードの未解決の `stopIncomplete` の項目（代行依頼）を、すべて解決済みにする。
4. 受信箱に info（宣言者と根拠）。

対象は、能力表の `stopDelegated` が真のノードだけ（CLI のノードは `notDelegated` で失敗し、`node.stop` の再試行を案内する）。
同じ `requestId` の再送は同じ結果を返し、記録は 1 回。宣言の後、アダプタは、そのノードを管理から外す（`release`）。

人間は、cli の `cso confirm-stopped <nodeId> [--note <根拠>]` か、画面の「止めたと宣言…」（ノード ID の打ち込みが要る。`docs/ui.md`）から宣言できる。

## 配線と紐付け（T21。**仮置き**）

Desktop の実機確認（Spike 01 の項目 1〜7）は、一部済んだ（親・子とも auto。範囲と未確認は、 [`docs/spikes/01-desktop-spawn-task.md`](spikes/01-desktop-spawn-task.md) の「確認項目と結果」の表）。**「再起動のあと」は、その結果で確定した。** ほかの手順（紐付け・能力表など）は、C1（Desktop の子の紐付けと報告）の確認まで**仮置き**のまま（この文書の変更では、実装は変えていない）。

### 配線

- daemon の設定 `childRuntime: "desktop"` で、木全体の子を Desktop の子として扱う（既定は `cli`。ノードごとの混在は扱わない）。
- フックのゲート（上の節）は、そのまま有効。`desktopRequireVerifiedHooks: false` にしない限り、Desktop の子は起動しない（`node.spawn` は起動の失敗になり、原因 `hooksUnverified` は記録に残る）。
- ファイルのフックの受け口（`POST /v1/hook`）は、Desktop の子には許可を返さない（フックの継承が未確認。項目 4）。
- 子のセッション識別子は、タスク生成の戻り値にない（項目 6）。アダプタは、`sessionId` にノード ID を入れて返す（**仮置き**。識別子が得られると分かったら、差し替える）。

### 紐付けの手順（案 A。最初のメッセージの後に、子が curl で結ぶ）

1. 親（統合セッション）が `node_spawn` で子を作る（pending なら、依存が揃って起動するまで待つ）。
2. 親が `node_bindCode`（`{ nodeId }`）を呼ぶ。daemon は一度きりの紐付けコード（10 分で失効）を新しく発行し、起動の文面（`instruction`: 子の ID・ブリーフ・紐付けと報告の手順）を返す。
3. 親は、`instruction` を、そのまま Desktop のタスク生成（spawn_task）に渡す。
4. 子は、最初のメッセージを受けたら、`instruction` にある `curl` で `POST /v1/bind` を呼び、ノードのトークンをシェルの変数 `CSO_TOKEN` に受け取る。以後の報告は、`curl` で `POST /v1/request`（`role: "child"`）。
   - トークンとコードは、`curl` の引数に置かない（`ps` のプロセス一覧に出さない）。本文とヘッダーは、シェルの組み込みの `printf` から標準入力で渡す（`-d @-`・`-H @-`）。トークンは、応答から直接変数に入れ、画面に出さない。
   - **仮置き**: Desktop の子が `curl` を実行できるか、MCP をあとから足せるかは、実機確認（項目 4）で確かめる。
   - Desktop の中間の統合ノード（role が integrator）は、紐付けできない（`node.bindCode` は `integratorNotSupported`。紐付けで渡すのは子のトークンだけ。**仮置き**）。

### 紐付けコードの扱い

- **コードは記録しない**: イベントログ（SQLite）・受信箱・記録（`note`・API のログ）には書かない。`node.bindCode` の応答（`instruction`）にだけ入る（試験で、SQLite のファイル・記録・受信箱にコードが残らないことを確かめている）。
- 窓口の重複の扱い（`docs/request-dedup.md`）は、処理中の同じ要求に同じ応答を返すだけで、結果を保存しない（終わったら消える）。
- **同じ `requestId` で再送すると、新しいコードを発行する**（前の応答を保存しないので、返せない。前のコードは、その時点で無効になる）。親は、最後に受け取った `instruction` を使う。
- 呼ぶたびに新しいコードになり、前のコードは無効になる。使ったコードは、もう使えない。daemon を再起動すると、コードはすべて無効になる。
- **注意（シェルの履歴など）**: `instruction` のコマンドの行には、紐付けコードがそのまま入る（`printf` の引数）。プロセス一覧には出ないが、子のシェルの履歴・端末のログ・会話の記録には残りうる。コードは一度きり・10 分で失効し、使ったあとは無効なので、残っても再利用はできないが、ほかへ書き写さない。トークンは、コマンドの行に書かず、応答から変数（`CSO_TOKEN`）に直接入れ、ヘッダーは標準入力から渡す（履歴にも `ps` にも出ない）。トークンは長く有効なので、書き出すと危ない。

### 再起動のあと

ここでの「再起動」は 3 つある。結果（Spike 01 の項目 7。親・子とも auto）と、今の実装・計画を分けて書く。

| 場合 | Desktop の子に起きること（実測） |
|:--|:--|
| 親（統合セッション）のアーカイブ | 子のプロセスは止まらず、最後まで走る。完了の知らせは、閉じた親には届かない |
| Desktop のアプリの再起動（作業中に終了して起動し直す） | 子のプロセスは止まる。約 30 秒後、アプリが自動で再開のメッセージを送り、新しいプロセス（`claude --resume`）で続きから走る。完了の知らせは、閉じた親に届かない。再開のメッセージは、フックでは人間の入力と区別できない |
| daemon の再起動 | Desktop の子は daemon の外で動くので、影響を受けない見込み（推測。daemon の再起動そのものは、項目 7 の確認の範囲の外）。コードから言えること: ノードのトークンは、ハッシュがファイルの表に保存され、再起動のあとも読み戻される（`credentials.ts`・`token-repository.ts`）ので失効しない。紐付けコードはメモリ上だけなので、再起動ですべて失効する（`api/bind.ts`） |

どの場合も、ワークツリーは消えない。Desktop の削除でも消えない（事実。手動確認の B6 のあとの片付けで分かった: `delete_session` は、子のワークツリーにコミットしていないファイルがあると、そのまま削除しない（強制削除を選ぶと、そのファイルも消える）。コミットしていないファイルがなければ削除できるが、その場合でも、ワークツリーは消えずに残る）。ワークツリーの回収は、Desktop の削除に任せられない。未確認: Cmd+W で閉じたとき、待機中にアプリを終了したとき、Manual・Bypass のとき、親を閉じた瞬間に動いていた長い単一のプロセス（ビルド・テストなど）が存続するか。

#### 今の実装

- daemon を再起動すると、アダプタ（`desktop-adapter.ts`）は何も管理していない（起動の指示も失われる）。起動時の照合（`reconcile.ts`）は、Desktop の子をプロセスで照合せず（daemon の外で動くので、作業ツリーのプロセスでは確かめられない）、状態を変えずに、**根の受信箱に、優先度のある項目（停止の代行依頼と同じ `stopIncomplete` の帯）を、まとめて 1 件**出す。対象は、記録で動作中・判断待ち・停止中・停止未完了の Desktop の子で、子の数と ID（5 件まで。残りは「ほか N 件」）を書く。未解決の同じ依頼があれば、出さない。
- **daemon は、子が止まったのか動いているのかを知らない**。記録の状態は、再起動の前のまま。人が確かめて、止めたと宣言する（`node.confirmStopped`）まで、記録は変わらない。
- 停止（代行依頼）と停止の宣言は、再起動のあとも使える（能力表どおり）。`node.bindCode` は、起動の指示がないので `notManaged`（止めたと宣言し、作り直す）。
- 親のアーカイブやアプリの再起動は、daemon には伝わらない。ファイルのフックの受け口（`POST /v1/hook`）は、`PreToolUse`・`PostToolUse`・`Stop` だけを受け、`UserPromptSubmit` を受けない。Desktop の子には許可を返さない（フック専用のトークンは CLI の子だけ）。アダプタの `send` は unsupported。したがって、アプリの自動の再開メッセージを、daemon が人の指示と取り違えることは、今はない。
- 親を閉じても、daemon の記録では子は動作中のまま残る。受信箱の停止の代行依頼は、閉じた親には届かない（人が受信箱で見る）。

#### 根の受信箱の 1 件で、人に確かめてもらうこと

項目 7 の結果から、**子は「止まっている」と決めつけられない**（親を閉じても、アプリを再起動しても、子は動き続けるか、自動で再開する）。受信箱の 1 件を見たら、人は、書かれた子ごとに、Desktop の画面で次を確かめる。

1. **子のセッションが、まだ動いているか**（作業中か、待機中か）。アプリを再起動した直後なら、約 30 秒待ってから見る（自動で再開することがある）。
2. **動いていて、続けてよいとき**: 何もしない（記録は動作中のまま）。子は、紐付けが生きていれば `report.done` で完了を報告する。アプリの再起動をまたいだ子は、トークンが失われている見込みなので、報告が届かないことがある（下の「計画」）。
3. **止めたいとき**: Desktop で子を止める（`stop_session` は今のターンだけを止める。項目 2）。**未確認: 作業中の子をアーカイブ・削除したときに、プロセスが止まるか**（B6 でアーカイブしたのは親で、子は止まらなかった。B3・B5 で削除したのはアイドルの子）。止まったことを、フックのログ（`PreToolUse`・`PostToolUse` が止まる）・ワークツリーの変化・`ps` で確かめてから、`cso confirm-stopped <nodeId> --note <根拠>` か、画面の「止めたと宣言…」で宣言する（宣言は取り消せない）。
4. **もう止まっているとき**（セッションがない・アーカイブ済み）: 同じく、止めたと宣言する。子の結果（コミット・差分）は、ワークツリーとブランチに残っているので、`git` で確かめてから宣言する（子のトランスクリプトは、閉じたあとは残らない）。

受信箱の 1 件の文面には、「（仮置き）」が残っている。文面の差し替えは、コードの変更になるので、別の作業で行う。

#### 計画（未実装）

- 子の完了は、親が閉じていても届く `report.done`（C1）に頼る。
- アプリの再起動をまたぐと子は新しいプロセスになるので、シェルの変数（`CSO_TOKEN`）に入れたトークンは失われる見込み。紐付けコードは一度きりなので、もう一度紐付ける手順（`node.bindCode` の再発行）か、トークンの持ち方（書き写さない原則と両立させる）を、C1・T21 で決める。親のアーカイブでは子のプロセスが続くので、変数も残る見込み（未確認）。
- 将来、`UserPromptSubmit` で人の介入を見て状態を動かすなら、アプリの自動の再開メッセージ（フックでは人間の入力と区別できない）を除く仕組みが要る（T21・Desktop の分で決める）。
