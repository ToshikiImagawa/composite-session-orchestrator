# プロジェクト原則

**バージョン**: 1.0.0
**最終更新日**: 2026-10-18
**ステータス**: 有効

## 目的

このドキュメントは、composite-session-orchestrator の開発を統制する非交渉原則と基準を定義します。すべてのコード、仕様、設計判断はこれらの原則に従う必要があります。

本プロジェクトは、複数の Claude セッションを「統合セッション 1 対 作業セッション n」の木構造で束ねる、単一開発者のローカル開発ツールです。構成は TypeScript の pnpm モノレポ（`packages/core`、`packages/daemon`、`packages/mcp`、`packages/cli`）と Claude Code plugin（`plugin/`）です。要求は `requirement/composite-session-orchestrator.md`（PRD）に定義されています。

## 原則階層

```
1. ビジネス原則（最優先）
   ↓
2. アーキテクチャ原則
   ↓
3. 開発手法原則
   ↓
4. 技術制約
```

優先度が高い原則が低い原則に優先します。

## 1. ビジネス原則（最優先）

### B-001: 破壊的操作は安全側に倒す

**原則**: 破壊的な操作は、失うものがある場合に拒否される安全な手段で行う。取り返しのつかない最終削除はエージェントに公開せず、エージェントに公開する破壊的操作は回収のみとする。会話記録（transcript）は Claude Code 側の管理物とし、本システムは削除しない。（PRD: NFR_006, DC_003, DC_004）

**適用範囲**: worktree・ブランチ・セッションに対するすべての回収、削除、停止の操作と、MCP で公開するすべてのツール

**検証方法**:

- [ ] 破壊的操作が、未コミットの変更や未マージのコミットなど失うものがある場合に拒否される
- [ ] 強制的な手段（強制削除、強制リセット等）を内部で使っていない
- [ ] 最終削除がエージェント向けの MCP ツールとして公開されていない（人間用の CLI のみが持つ）
- [ ] transcript を削除する処理が存在しない

**違反例**:

- 失うものの有無を確認せずに worktree を強制削除する
- 子セッションが呼べる MCP ツールに最終削除を含める
- 回収時に transcript ファイルを削除する

**準拠例**:

- 回収判定が「失うものがあるか」を先に評価し、ある場合は拒否して理由と次の操作を返す
- 最終削除は `orch purge` など人間用コマンドに限定する

---

### B-002: 単一の状態と完全な操作記録

**原則**: 状態は daemon が単一に保持し、統合セッション、子セッション、HTML 画面は同じ状態を参照する。すべての操作、判断、範囲違反、状態遷移を時系列で記録する。（PRD: NFR_001, NFR_011）

**適用範囲**: 状態の保持・変更・参照のすべて

**検証方法**:

- [ ] daemon 以外が状態の写しを独自に保持し、更新していない
- [ ] 状態を変える操作が、必ずイベントログに記録される
- [ ] 範囲違反や拒否された操作もログに残る
- [ ] ログから木の状態を再現できる

**違反例**:

- CLI や MCP が状態を直接ファイルに書き込む
- 拒否した操作をログに残さない

**準拠例**:

- 状態の変更はすべて daemon 経由で行い、変更と同時にイベントを追記する
- 再起動後もイベントログから状態を復元する

## 2. アーキテクチャ原則

### A-001: 純粋なドメイン層（core）

**原則**: `packages/core` は I/O を持たない純粋なドメイン層とし、`daemon`、`mcp`、`cli` が `core` に依存する。依存は常に外側から `core` への単方向とし、`core` は他のパッケージに依存しない。回収判定、受信箱の整列、親子の不変条件は決定的な純粋関数で実装する。（PRD: NFR_007）

**適用範囲**: すべてのパッケージの依存関係と `packages/core` の実装

**検証方法**:

- [ ] `packages/core` の依存に `node:fs`、`node:child_process`、ネットワーク、時刻・乱数の直接参照がない
- [ ] `packages/core/package.json` が他のワークスペースパッケージに依存していない
- [ ] パッケージ間に循環依存がない
- [ ] 時刻や識別子などの外部要因は引数として受け取る

**違反例**:

- `core` からファイルシステムや git コマンドを直接呼ぶ
- `core` が `daemon` の型を import する
- `daemon` と `mcp` の間で相互参照する

**準拠例**:

- 回収判定が「現在の状態を入力にして判定結果を返す」純粋関数になっている
- I/O は `daemon` のアダプタに閉じ込め、`core` には結果だけを渡す

---

### A-002: Library-First

**原則**: 可能な限り既存ライブラリを活用し、車輪の再発明を避ける。

**適用範囲**: すべての実装

**検証方法**:

- [ ] 新規実装前に既存ライブラリを調査したか
- [ ] 自作する場合の明確な理由があるか
- [ ] 依存を追加する際は、着手時点の最新版を確認して固定している

**違反例**:

- ライブラリ調査なしで自作実装
- スキーマ検証や MCP プロトコルの処理を独自に実装する

**準拠例**:

- MCP TypeScript SDK、Claude Agent SDK、zod など既存ライブラリを選定して利用する
- 自作する場合は理由を設計に明記する

## 3. 開発手法原則

### D-001: Test-First

**原則**: テストを先に書いてから実装する（TDD）。テストツールは Vitest を想定する。`core` の不変条件は fast-check による性質ベーステストで検証する。

**適用範囲**: すべてのコア機能。特に `packages/core` の判定ロジックと不変条件

**検証方法**:

- [ ] 実装前にテストケースが作成されている
- [ ] 失敗するテストを先に書き、実装で通すフローを遵守している
- [ ] `core` の不変条件（親子関係、状態遷移、受信箱の順序）に性質ベーステストがある
- [ ] 冪等であるべき操作（生成、判断要求、回収、回答登録）に再試行のテストがある

**違反例**:

- 実装完了後にテストを追加
- 不変条件を具体例のテストだけで確認する

**準拠例**:

- Red → Green → Refactor のサイクルを遵守
- 任意の木に対して不変条件が保たれることを fast-check で検証する

---

### D-002: Specification-Driven

**原則**: 仕様書なしで実装しない。

**適用範囲**: すべての新機能・変更

**検証方法**:

- [ ] `specification/` に抽象仕様書が存在する（`{feature-name}.md` または `{feature-name}_spec.md`）
- [ ] チケット作業中は `task/{ticket-number}/design-draft.md` に技術設計が存在する
- [ ] クリーンアップ時に決定が `adr/{feature-name}.md` に記録される
- [ ] 仕様書が最新（実装前に更新されている）

**違反例**:

- 口頭指示のみで実装開始
- 仕様書が古いまま実装

**準拠例**:

- Specify → Plan → Tasks → Implement のフローを遵守
- PRD と仕様書を真実の源（Single Source of Truth）として管理

## 開発標準

### コード品質

| 標準          | 要件                         | ツール                    | 適用方法                     |
|:------------|:---------------------------|:-----------------------|:-------------------------|
| **型安全性**    | strict、noUncheckedIndexedAccess、exactOptionalPropertyTypes を維持 | TypeScript（`tsconfig.base.json`） | `pnpm typecheck`、CI |
| **Linting** | エラー・警告ゼロ                   | 別 PR で導入               | `pnpm lint`、CI           |
| **重複**      | 同じロジックを複数箇所に持たない           | -                      | セルフレビュー                  |

### ドキュメント

| 標準         | 要件                        | 配置場所                  | 更新頻度   |
|:-----------|:--------------------------|:----------------------|:-------|
| **要求**     | PRD に要求 ID（UR/FR/NFR/DC）を定義する | `${SDD_ROOT}/requirement/` | 要求の変更時 |
| **仕様書**    | すべての機能に抽象仕様書が必要           | `${SDD_SPECIFICATION_PATH}/` | 実装前    |
| **設計ドラフト** | 作業中のチケットに `design-draft.md` が必要（一時）     | `${SDD_TASK_PATH}/{ticket-number}/` | 設計フェーズ |
| **決定ログ**   | 確定した決定は機能の決定ログのエントリとして残す  | `${SDD_ADR_PATH}/` | タスククリーンアップ時 |
| **技術検証**   | 実装前の技術検証の手順と結果を記録する       | `docs/spikes/`        | 検証の実施時 |
| **README** | 最新のセットアップ手順               | プロジェクトルート             | 必要に応じて |

### テスト

| 標準             | 要件                     | 適用方法          | 例外 |
|:---------------|:-----------------------|:--------------|:---|
| **ユニットテスト**    | `core` の判定・不変条件を網羅する   | `pnpm test`、CI | -  |
| **性質ベーステスト**   | `core` の不変条件を fast-check で検証 | `pnpm test`、CI | -  |
| **結合テスト**      | すべてのメインフローをカバー         | セルフレビュー       | -  |
| **エッジケース**     | 境界条件をテスト               | セルフレビュー       | -  |

### セキュリティ

| 標準           | 要件                                | 適用方法           | レビュー頻度 |
|:-------------|:----------------------------------|:---------------|:-------|
| **接続元の制限**   | ローカルからの接続のみ受け付け、ノードごとの資格情報で識別する（NFR_005） | テスト            | 各 PR   |
| **役割別の公開**   | 各セッションには役割に応じた操作だけを公開する（NFR_004） | インスペクション       | 各 PR   |
| **入力検証**     | MCP・CLI・フックからのすべての入力を検証する | テスト            | 各 PR   |
| **シークレット管理** | コードやログに資格情報を含めない                 | セルフレビュー、CI     | 各コミット  |

## アーキテクチャ制約

### 依存方向

```
cli ─┐
mcp ─┼─→ core
daemon ┘
```

**ルール**:

- `daemon`、`mcp`、`cli` は `core` に依存してよい
- `core` は他のワークスペースパッケージに依存してはならない
- 循環依存禁止
- 状態の保持と変更は `daemon` に集約する

### 技術スタック制約

| レイヤー        | 許可される技術                       | 禁止事項              | 理由               |
|:------------|:------------------------------|:------------------|:-----------------|
| **言語**      | TypeScript（ESM、Node.js 20 以上）  | 型なしの JavaScript   | 型安全性、一貫性         |
| **パッケージ管理** | pnpm（ワークスペース）                | npm / yarn の併用    | ロックファイルの一貫性      |
| **MCP**     | MCP TypeScript SDK、zod         | 独自プロトコルの実装        | Library-First    |
| **テスト**     | Vitest、fast-check（導入は別 PR）    | 複数のテストランナーの併用     | 構成の単純さ           |
| **提供形態**    | Claude Code plugin（private marketplace） | -                 | PRD DC_001       |

**例外プロセス**: ADR に理由を記録したうえで変更する

### モジュール構成

```
packages/
├── core/     # ドメイン（純粋、I/O なし）
├── daemon/   # イベントログ、ランタイムアダプタ、フック受付、HTML 画面
├── mcp/      # MCP ツール定義、ロール別の公開、エラー設計
└── cli/      # 人間用コマンド
plugin/       # 役割定義 skill、hooks、MCP 設定、起動コマンド
```

## 意思決定フレームワーク

技術的トレードオフに直面した場合、以下の順序で優先順位付けします：

1. **正確性** - 仕様を満たしているか？
2. **安全性** - データや作業を失わないか？
3. **シンプルさ** - 最もシンプルな解決策か？
4. **保守性** - 保守可能か？
5. **パフォーマンス** - 十分に高速か？
6. **開発者体験** - 作業しやすいか？

**タイブレーカー**: 後で変更しやすい方を選択

## 品質ゲート

ローカルで実行するチェックと CI のチェックは、同じスクリプトを使います。CI にだけ存在するチェックや、CI とは別の手順を持つローカルチェックを作りません。CI は ubuntu と macOS の両方で実行します。

### Pre-Commit

- [ ] `pnpm typecheck` が通る
- [ ] `pnpm lint` が通る（導入後）
- [ ] ローカルでテストが通る
- [ ] シークレットが含まれていない

### Pre-PR

- [ ] `pnpm build`、`pnpm typecheck`、`pnpm lint`、`pnpm test` がすべて通る
- [ ] `plugin/` の構造（`plugin.json` を含む）を検証するスクリプトが通る
- [ ] 仕様整合性を確認（`/check-spec`）
- [ ] 仕様書・設計書を更新

### Pre-Merge

- [ ] CI が ubuntu と macOS の両方で成功
- [ ] マージコンフリクトなし
- [ ] ドキュメント更新

## 4. 技術制約

### T-001: TypeScript strict

**原則**: `tsconfig.base.json` の `strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes` を維持し、各パッケージはこれを継承する。

**適用範囲**: すべてのソースコード

**検証方法**:

- [ ] すべてのパッケージの `tsconfig.json` が `tsconfig.base.json` を継承している
- [ ] strict 系のオプションを無効化・上書きしていない
- [ ] `any` や型アサーションを、理由なく使っていない

**違反例**:

- パッケージ側で `strict: false` に上書きする
- 配列の添字アクセスの `undefined` を無視して型アサーションで通す

**準拠例**:

- 型ガードと `unknown` で入力を絞り込む
- 任意の値を zod で検証してから型付きで扱う

---

### T-002: No Runtime Errors

**原則**: 実行時エラーを許容しない（コンパイル時に検出）。失敗は原因と次に取るべき操作を示して返す。（PRD: NFR_010）

**適用範囲**: すべてのコード

**検証方法**:

- [ ] strict モードが有効
- [ ] 型ガードの適切な使用
- [ ] エラーハンドリングが網羅的
- [ ] 失敗時の応答に原因と次の操作が含まれる

**違反例**:

- `any` 型の多用
- try-catch のない非同期処理
- 未処理の Promise rejection

**準拠例**:

- すべての関数に明確な型定義
- エラーケースの網羅的なハンドリング
- Result 型の活用

---

### T-003: ローカル限定とノード単位の資格情報

**原則**: システムはローカルからの接続のみを受け付け、ノードごとの資格情報で接続元を識別し、ノード停止時に失効させる。（PRD: NFR_005）

**適用範囲**: `daemon` の受け付け口と、資格情報を扱うすべてのコード

**検証方法**:

- [ ] ローカル以外のインターフェースで待ち受けていない
- [ ] 接続元がノードごとの資格情報で識別される
- [ ] ノード停止時に資格情報が失効する
- [ ] 資格情報がログや画面に出力されない

## 原則追加のガイドライン

新しい原則を追加する際は、以下を考慮してください：

### 良い原則の条件

| 条件        | 説明                         |
|:----------|:---------------------------|
| **検証可能**  | チェックリストで検証できること            |
| **明確**    | 曖昧さがなく、準拠/違反の判断が明確であること    |
| **正当化可能** | なぜその原則が必要かが説明できること         |
| **実現可能**  | 単一の開発者が実践できること             |
| **永続的**   | 一時的な方針ではなく、長期的に守るべき原則であること |

### 追加プロセス

```
1. 提案（Issue 等に記録）
   ↓
2. 原則ファイルに追加
   ↓
3. バージョンをマイナーアップ（例: 1.0.0 → 1.1.0）
   ↓
4. 影響を受けるドキュメントを更新
   ↓
5. /constitution validate で検証
```

## コンプライアンス

### 適用メカニズム

**自動化**:

- CI（ubuntu / macOS）で、ローカルと同じスクリプトを実行する（型検査、lint、テスト、plugin 構造の検証）

**手動**:

- セルフレビュー（アーキテクチャ、設計判断）
- PR 作成前の原則準拠の確認

### 違反への対処

| 重大度    | 対応                 | 例                          |
|:-------|:-------------------|:---------------------------|
| **重大** | 即座にマージをブロック        | テストなし、破壊的操作の安全装置の欠如、`core` への I/O 混入 |
| **主要** | 明示的な正当化が必要         | ADR なしのカスタム実装              |
| **軽微** | 現在の PR またはフォローアップで修正 | 軽微なドキュメント更新                |

### 例外プロセス

原則の遵守が不可能な場合：

1. **文書化**: アーキテクチャ決定記録（ADR）を作成
2. **正当化**: なぜ原則に従えないか説明
3. **緩和**: 補償統制を説明
4. **追跡**: 技術的負債として記録
5. **計画**: 解決のタイムラインを設定（一時的な場合）
